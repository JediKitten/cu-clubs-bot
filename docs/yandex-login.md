## Настройка приложения

В [Яндекс OAuth](https://oauth.yandex.ru/) создать приложение **для авторизации
пользователей** (не тип «для доступа к API»).

| Поле | Значение |
|---|---|
| Название | CU Clubs |
| Описание | Вход в бот студенческих клубов Центрального университета с университетской почтой |
| Платформа | Веб-сервисы |
| Redirect URI | `https://de.devbox.cu3rd.ru/auth/yandex/callback` |
| Разрешение API Яндекс ID | Адрес электронной почты — `login:email` |

Не запрашивать почтовый ящик, Диск, аватар, телефон, дату рождения или другие
разрешения. Контакты и правовые сведения приложения заполняет владелец своими
актуальными данными; их нельзя придумывать. Client ID можно передать разработчику.
Client secret сохраняется в закрытой конфигурации, не в публичном репозитории,
описании PR, ссылке, скриншоте или сообщении боту.

## Конфигурация сервера и self-service

Текущее размещение — прежний сервер. Caddy публикует только `/auth/yandex/start`
и `/auth/yandex/callback` под существующим devbox-хостом. Self-service использует
другую БД, его worker выключен и пока не участвует в этом входе. На devbox
`/health/ready` возвращает 404 намеренно: остальные пути приложения, включая
клубный REST API, там не опубликованы. Общая передача — [handover.md](handover.md).

Приложение читает:

```dotenv
CU_CLUBS_YANDEX_AUTH_ENABLED=true
CU_CLUBS_YANDEX_CLIENT_ID=<Client ID приложения>
CU_CLUBS_YANDEX_CLIENT_SECRET=<только закрытый секрет>
CU_CLUBS_YANDEX_REDIRECT_URI=https://de.devbox.cu3rd.ru/auth/yandex/callback
```

Используются уже имеющиеся `CU_CLUBS_VERIFICATION_SECRET` (не менять при переносе)
и `CU_CLUBS_TELEGRAM_BOT_USERNAME`. Схема БД — миграция `20261116_0014`.

Для self-service потребуется отдельное штатное изменение проекта: объявить
`CU_CLUBS_YANDEX_CLIENT_SECRET` в `apps.api.secrets`, остальные три ключа — в
`apps.api.variables`, затем обновить доставку с новым sealed secret. Текущий
tag-only helper намеренно не добавляет произвольные секреты или настройки.
Секрет шифруется штатными инструментами платформы, его plaintext не копируется
в Actions. Применение этих mappings на целевой площадке не подтверждено; наличие ключей
на старом сервере не обновляет sealed delivery.

Два браузерных маршрута существуют вне делегированного API клубных ботов:
`GET /auth/yandex/start` и `GET /auth/yandex/callback`. При выключенном флаге
возвращают 503. Точный callback должен быть разрешён настройками OAuth.
Приложение скрывает query этих путей в своём access logger; при включении
также проверить, что пограничный HTTP-прокси не сохраняет параметры OAuth
`code`, `state` и стартовый ticket в открытых логах.

## Поведение

Студент/сотрудник → ФИО → «Войти через Яндекс» → вход университетским аккаунтом
→ возврат в бот → «Проверить вход» → предпросмотр почты и ФИО → «Подтвердить
привязку» → исходная встреча, QR, согласие API или профиль. Набранная вручную
почта не является доказательством. Гости проходят отдельный ввод ФИО и
предпросмотр; предварительная запись остаётся закрытой, доступен гостевой QR
встречи с одним клубом Seed+.

Сервер запрашивает только `login:email`, обменивает код через TLS с Basic
client authentication и PKCE S256. Проверяет `client_id`, ID аккаунта и
**только `default_email`** из Яндекса: домен должен в точности равняться
`edu.centraluniversity.ru`. Список внешних/дополнительных адресов не используется
как обход. Токены Яндекса не сохраняются в БД или браузере. В ответе token отсутствие
`scope` допускается; явно присутствующий scope обязан содержать `login:email`.
Факт получения token не отменяет последующую проверку профиля.

Одноразовое состояние связано с secure/HttpOnly/SameSite=Lax cookie конкретного
браузера и сроком 10 минут. Повтор callback, чужая cookie, истёкшая/отменённая
ссылка и неверная почта не подтверждают профиль. Новая ссылка отменяет старую;
на аккаунт не более пяти начал в час. Даже успешный callback только готовит
кандидата: привязка выполняется после подтверждения исходным числовым Telegram
ID. Это защищает от пересылки ссылки. Уже занятая почта не передаётся другому
аккаунту. Импортированная история присоединяется существующим сервисом с
сохранением посещений, ответов и клубных прав; спорный конфликт не затирается.

Университетский SSO на стороне Яндекса зависит от настроек организации.
Документация Яндекса не подтверждает, что именно домен ЦУ обязательно направляет
в LMS. Владение университетским аккаунтом также не является отдельным
утверждением о текущем зачислении; бот подтверждает доступ к этой почте.

## Оставшаяся сквозная приёмка

Локальные проверки используют подставной провайдер, а не настоящие токены:
PKCE/state/cookie/replay/expiry, чужой Telegram ID, ошибочный домен/приложение,
предпросмотр и подтверждение, сохранение имени/возвраты, присоединение импорта,
закрытые ответы браузеру и отсутствие кодов в access logger.

Остаются живые проверки с владельцем: университетский аккаунт (включая реальный
переход SSO/LMS), личный аккаунт Яндекса, отказ доступа, истёкшая/повторная ссылка,
возврат в исходный сценарий Telegram. Флаг включён в разрешённом тестовом контексте для этой приёмки;
перед рабочим запуском нужно завершить сквозные проверки. Сам факт успешных локальных тестов не доказывает SSO.

Источники: [регистрация приложения](https://yandex.ru/dev/id/doc/ru/register-client),
[authorization code, state и PKCE](https://yandex.ru/dev/id/doc/ru/codes/code-url),
[userinfo и default_email](https://yandex.ru/dev/id/doc/ru/user-information),
[настройка SSO организации](https://yandex.ru/support/yandex-360/business/admin/ru/sso/setup).

## Повторная проверка и диагностика для новой команды

1. Из нового шага в Telegram получить **новую** ссылку. Старые, повторные и
   истёкшие ссылки не восстанавливать вручную и не менять строки challenge в БД.
2. Пройти вход именно университетским аккаунтом, вернуться в исходный бот,
   нажать «Проверить вход», сверить ФИО/почту и подтвердить исходным Telegram ID.
3. Отдельно проверить отказ провайдера, личный адрес, истечение и возвращение
   к исходной встрече/QR/API-согласию. Проверка server health не заменяет эти шаги.
4. При отказе различать фиксированные причины журнала: stage `token`/`userinfo`,
   HTTP status, boolean совпадения client/email/subject. Они не содержат
   email, token или authorization code. Не включать verbose HTTP bodies/headers
   и OAuth query в журналы ради диагностики.
