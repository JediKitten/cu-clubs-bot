## Коротко о системе

CU Clubs — Telegram-бот клубов ЦУ и HTTP API для внешних клубных ботов.
Монорепозиторий содержит Python-приложение, миграции, тесты, конфигурации
размещения, документацию и исходники Figma-плагина для дайджеста.
Работает прежний сервер. Подготовленный self-service — отдельное окружение,
не действующая БД и не основание для переключения бота при передаче.

## Версия и воспроизводимость

`Jedi_kitten/cu-clubs-bot`. Последняя отправка прикладного кода в GitHub успешна;
Forgejo SSH:2222 был недоступен. Документационный commit может быть новее
установленного кода; его hash не следует выдавать за серверную версию.

Работающий локальный Docker tag получен небольшими исправлениями поверх образа
`git.cu3rd.ru/jedi_kitten/cu-clubs-bot:091de0d851a6c8adcf1e4fe1fb1d7b4333c6d529`.
Сначала добавлен патч навигации `dc566ea`, затем `b6d4531` (Яндекс и меню после
копий). Это **локальный** образ прежнего сервера, не опубликованный registry tag.
Не выбирайте образ только по строке tag и не запускайте обычный server-up.sh
как универсальное обновление текущего выпуска: он не учитывает release overlay.

Новая команда может собрать полный образ из зафиксированного Git commit;
подробный порядок и сохранение настроек описаны в [deployment.md](deployment.md).
Полная пересборка в рамках этой проверки документации не выполнялась.
До следующего выпуска сохраните текущий overlay и образ для возврата, права
на volumes, секреты и текущую схему. Изменение схемы БД не откатывается простой
заменой Docker image. Автоматический перенос данных старого legacy-бота не нужен
по решению владельца; действующая БД нового бота — отдельные текущие данные.

## Настройки, о которых важно знать

- Яндекс и внешняя Telegram-доставка включены; SMTP не настроен.
- `test_self_registration_enabled=true` и `test_allow_unverified_leaders=true`.
  Это временные исключения, не подтверждение университетской личности.
- Sheets sync/writes включены; рабочая цель совпадает с явно разрешённой
  тестовой копией. OAuth JSON присутствует, живой refresh сейчас не проверялся.
- API включён, лимит 120/min, TTL пользовательского grant 90 дней.
- Backups включены; файл остаётся в чате. После копии первое действие переносит
  меню вниз. Если удалить старое сообщение нельзя, кнопки снимаются по возможности.
- `self_service_pooler=false` на действующем сервере. Не переносить настройки
  pooler/self-service на старый PostgreSQL механически.

[Полный справочник настроек](configuration.md). `.env.example` — безопасный
локальный шаблон, не копия текущего сервера.

## Первые действия принимающей команды

1. Получить доступы, проверить checkout и прочитать `AGENTS.md`, статус, API и
   размещение. До изменения процессов сверить Compose-файлы и текущий image.
2. Прочитать состояние API/worker/db и проверить loopback readiness. При необходимости
   открыть локальный API через SSH tunnel, не публикуя его в сеть.
3. С владельцем выполнить свежий Яндекс-вход и подтверждение в Telegram, затем
   принять первый переход меню после реальной доставленной резервной копии.
4. Пройти минимальные ролевые сценарии: создание/согласование/отмена встречи,
   регистрация, QR/импорт, возвраты, опрос, клиент API с отдельным согласием.
5. Создать актуальную копию и проверить восстановление **в отдельную БД**.
   Последние старые отчёты восстановления не заменяют приёмку новой командой.
6. Учесть технические gaps: неполная EventOutput в OpenAPI при полном HTTP JSON;
   CalendarSync не создаёт годовые листы/недели, имеет `unbounded_week` и не
   обеспечивает общий CAS Google; параметр цвета пока не влияет на фиксированный
   `#FF00FF`. FAQ при включённой саморегистрации может описывать ручной логин
   вместо Яндекса. Подробности в статусе и тематических контрактах.
7. Зафиксировать владельцев доступов, рабочий режим, очередь задач и критерии
   завершения. Приоритеты из открытого списка назначает владелец продукта.

Дальнейший перенос self-service, включение SMTP, рабочей таблицы или публичного
API — отдельные изменения. Передача документации их не запускает.

## Как быстро диагностировать

Команды выполняются **на действующем сервере** из `/home/kir/cu-clubs-bot`:

```sh
dc() { docker compose -f compose.server.yaml -f compose.release-20261116.yaml "$@"; }
dc ps
curl --fail --silent --show-error http://127.0.0.1:8310/health/ready
dc exec -T worker python -c 'import time; from pathlib import Path; print(round(time.time()-Path("/tmp/cu-clubs-worker-heartbeat").stat().st_mtime, 1))'
dc exec -T db psql -U cu_clubs -d cu_clubs -At -c 'SELECT version_num FROM alembic_version;'
dc exec -T db psql -U cu_clubs -d cu_clubs -c 'SELECT status, count(*) FROM outbox GROUP BY status;'
```

| Симптом | Что проверить |
|---|---|
| Public `/health/ready` даёт 404 | На OAuth-host это ожидаемо: опубликованы только auth paths; проверять loopback |
| `/auth/yandex/*` даёт 503 | Флаг/ключи/callback в приложении; healthy API не означает настроенный OAuth |
| OAuth start без ссылки даёт 400 | Одноразовый ticket обязателен; получить новую ссылку в боте |
| Яндекс «вход не завершён» | Свежая ссылка, университетский default_email, client_id и безопасная причина stage/status в API log; не обходить доменную проверку |
| Бот не отвечает | Один polling worker, heartbeat, db, inbox/outbox; не добавлять второй poller |
| Сообщение не повторилось | Проверить failed/uncertain и активный диалог; uncertain не повторять вслепую |
| Sheets не меняется | Тестовая цель, разрешение writes, Google refresh и calendar_bindings/conflicts |
| Обычное обновление потеряло патч | Проверить оба Compose-файла и фактический image; не выполнять второй rollout для диагностики |

Секреты, OAuth query, payload/ФИО и данные участников не включать в общий
диагностический отчёт. Безопасные auth logs дают этап и класс причины.
