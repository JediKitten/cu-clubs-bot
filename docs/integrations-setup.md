# Подключение почты и личного Google-аккаунта

Актуальность инструкции и официальных источников проверена 12 ноября 2026.
Личный Google OAuth уже подтверждён: чтение метаданных тестовой книги проверено
локально и с сервера. SMTP остаётся отложенным до настройки DNS отправителя.
Ниже сохранена инструкция для повторной авторизации и последующего подключения почты.
Не вставляйте пароли, JSON credentials и токены в чат или Git.

## 1. Что подключаем

Это две независимые настройки:

- **Почта** отправляет коды студентам через SMTP. Для собственного адреса
  предлагается `cuclubs@cu3rd.ru` через Resend после подтверждения домена.
  Альтернатива для временного Gmail-отправителя — пароль приложения,
  если Google разрешает его создать.
- **Google Sheets** работает с уже созданной тестовой копией календаря от имени
  личного аккаунта через OAuth. Вход в Google в Codex не выдаёт доступ серверу бота.

Временный Gmail-адрес указывается честно в поле отправителя. Университетский адрес
нельзя указывать без разрешённой настройки отправки от него. Позже можно заменить
SMTP-провайдера и отправителя. Коды, их срок действия и ограничения попыток
контролирует приложение; SMTP-адаптер только доставляет письмо.

## 2. Собственный отправитель `cuclubs@cu3rd.ru` через Resend

Это предложенный адрес: он ещё **не подключён**, DNS и аккаунт Resend этой
инструкцией не создаются. После проверки права на домен Resend разрешает
отправлять с любого адреса этого домена без отдельной регистрации имени
`cuclubs`. Настройка исходящей почты сама по себе не создаёт почтовый ящик для
получения ответов. Если нужны входящие, позже отдельно настраиваются mailbox,
пересылка либо receiving; сейчас для доставки кодов это не требуется.
Источник: [адреса отправителя](https://resend.com/docs/knowledge-base/how-do-I-create-an-email-address-or-sender-in-resend).

Этот путь удобен для своего домена: уже подготовленный SMTP-адаптер подходит,
Gmail-аккаунт с именем `cuclubs` и Google app password для почты не нужны.
Google Sheets OAuth остаётся отдельным подключением личного аккаунта.

### Регистрация владельца

1. Откройте [регистрацию Resend](https://resend.com/signup) и нажмите
   **Log in with Google**; войдите самостоятельно своим аккаунтом. Возможны
   также GitHub или регистрация по существующей почте и новому паролю.
   Пароль, дату рождения и другие личные данные за владельца не придумываем.
2. До завершения регистрации прочитайте условия: на странице указано, что
   регистрация означает согласие с Terms, Acceptable Use и Privacy Policy.
   Этот шаг и вход выполняет владелец. Платную подписку и pay-as-you-go для
   тестового подключения не включаем.

### Домен и DNS

3. В панели **Domains → Add Domain** добавьте `cu3rd.ru`, если нужен именно
   `cuclubs@cu3rd.ru`. Выберите предлагаемый регион, затем откройте **Records**.
   Провайдер рекомендует отдельные поддомены для разделения репутации; вариант
   `cuclubs@mail.cu3rd.ru` потребует отдельной проверки `mail.cu3rd.ru` и будет
   другим адресом. Здесь сохраняем предложенный адрес на корневом домене.
4. Скопируйте **точные** имена, типы, значения и приоритеты DNS из этой панели.
   До появления этих данных не используйте выдуманные DKIM-ключи или записи из
   примеров. Для новых доменов Resend может выдать CNAME вместо старой пары
   MX+TXT. Записи должны полностью совпадать с выданными для этого домена.
5. Перед добавлением проверьте существующие записи и конфликт имён. Не заменяйте
   рабочие MX корневого домена, A/AAAA сайтов, существующий SPF или DMARC вслепую.
   Sending использует отдельный Return-Path, обычно `send.cu3rd.ru`; его MX
   обслуживает возвраты, а не создаёт входящий ящик `cuclubs@`. При конфликте
   имени Return-Path выбирается другое свободное имя в панели. Для CNAME на
   том же имени не должно быть иных записей.
6. Добавьте согласованные записи у DNS-провайдера. CNAME для Resend должен быть
   без HTTP-проксирования. Дождитесь **Verified** в панели: обычно это минуты,
   но распространение DNS может занять до 72 часов. DMARC проверяется отдельно
   с учётом уже существующей политики домена.
7. **Receiving не включаем** для исходящих кодов. Его отдельный MX может изменить
   маршрутизацию входящих писем домена. Если понадобится входящая почта,
   сначала выбираем отдельную схему приёма и проверяем текущий почтовый сервис.

Источники: [добавление и проверка домена](https://resend.com/docs/add-a-domain),
[Return-Path, CNAME с августа 2026 и конфликты MX](https://resend.com/docs/knowledge-base/how-do-i-avoid-conflicting-with-my-mx-records),
[отдельная настройка receiving](https://resend.com/docs/dashboard/receiving/custom-domains).

### Ключ и подключение к боту

8. В **API Keys → Create API Key** задайте имя `CU Clubs SMTP`, разрешение
   **Sending access** и ограничьте ключ подтверждённым доменом `cu3rd.ru`.
   Ключ показывается только один раз. Сохраните его напрямую в закрытый `.env`
   или хранилище секретов; не отправляйте в чат и не добавляйте в Git.
9. Настройки проекта:

   ```dotenv
   CU_CLUBS_SMTP_HOST=smtp.resend.com
   CU_CLUBS_SMTP_PORT=465
   CU_CLUBS_SMTP_USE_SSL=true
   CU_CLUBS_SMTP_STARTTLS=false
   CU_CLUBS_SMTP_USERNAME=resend
   CU_CLUBS_SMTP_PASSWORD=replace-with-private-resend-api-key
   CU_CLUBS_SMTP_SENDER=cuclubs@cu3rd.ru
   ```

   Строка password — заглушка. SMTP-паролем служит Resend API key, не пароль
   Google и не пароль входа в Resend. Альтернатива — порт `587` с
   `SMTP_USE_SSL=false`, `SMTP_STARTTLS=true`.
10. После Verified и сохранения ключа выполните одну явную тестовую отправку
    на согласованный собственный адрес. Проверьте её в панели **Emails**,
    а затем во входящих/спаме получателя. Это будет фактическая проверка
    отправителя; до неё нельзя считать почту подключённой.

Источники: [Sending access и ограничение ключа доменом](https://resend.com/docs/create-an-api-key),
[точные SMTP credentials и порты](https://resend.com/docs/send-with-smtp).

### Бесплатный запуск и ограничения получателей

На дату проверки тариф **Free** стоит $0 и включает **3 000 писем в месяц**,
**100 за календарный день UTC** и до **3 доменов**. В Москве дневной лимит
сбрасывается в 03:00. Это объём писем, не число пользователей: повторные коды
тоже расходуют лимит. При включённом receiving входящие тоже учитываются.
Перед запуском сверяем объём регистраций с лимитом, платное превышение
автоматически не включаем. Источники: [текущий тариф](https://resend.com/pricing),
[актуальные квоты и правило UTC-дня](https://resend.com/docs/knowledge-base/account-quotas-and-limits).

Пока используется тестовый отправитель `onboarding@resend.dev`, разрешён только
адрес, связанный с аккаунтом Resend. Для писем студентам нужны свой подтверждённый
домен и соответствующий From. На бесплатном аккаунте отдельное production
approval не требуется; подтверждение домена остаётся обязательным.
Источники: [ограничение resend.dev](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain),
[production-доступ бесплатного аккаунта](https://resend.com/docs/knowledge-base/does-resend-require-production-approval).

## 2а. Альтернатива: почта через личный Gmail

1. Откройте [безопасность Google-аккаунта](https://myaccount.google.com/security)
   нужного отправителя и включите **двухэтапную аутентификацию**.
2. Откройте [пароли приложений](https://myaccount.google.com/apppasswords).
   Создайте отдельный пароль с названием, например `CU Clubs test SMTP`.
   Если раздел недоступен, обычный пароль аккаунта не подойдёт. Возможные причины:
   Advanced Protection, вход только через ключи безопасности или ограничения
   организации. В таком случае выбираем другой SMTP или отдельно внедряем OAuth
   для почты; Sheets OAuth не даёт SMTP-доступ автоматически.
3. В локальном `.env` укажите реальные значения вместо примеров:

   ```dotenv
   CU_CLUBS_SMTP_HOST=smtp.gmail.com
   CU_CLUBS_SMTP_PORT=587
   CU_CLUBS_SMTP_USE_SSL=false
   CU_CLUBS_SMTP_STARTTLS=true
   CU_CLUBS_SMTP_USERNAME=your-account@gmail.com
   CU_CLUBS_SMTP_PASSWORD=app-password-without-spaces
   CU_CLUBS_SMTP_SENDER=your-account@gmail.com
   ```

   Это пример, не готовые credentials. Пароль вводится только в закрытый локальный
   файл. Порт 587 используется с STARTTLS. Альтернатива — порт 465 с
   `SMTP_USE_SSL=true`, `SMTP_STARTTLS=false`. Один из двух режимов обязателен;
   проверка сертификата не отключается.
4. После заполнения отдельно запустите согласованную тестовую отправку на свой
   адрес и проверьте входящие и спам. Ответ SMTP означает приём сервером, получение
   письма подтверждается в ящике. Самостоятельно сообщения при старте не уходят.
5. Для университетского отправителя запросите у университета SMTP host, port,
   режим защиты, username, credential и разрешённый From. Замените настройки и
   повторите тест. Смена пароля Google отзывает пароли приложений.

Источники: [пароли приложений и ограничения](https://support.google.com/accounts/answer/185833),
[защищённые SMTP-порты Gmail](https://developers.google.com/workspace/gmail/imap/imap-smtp).

## 3. Google Cloud: один проект для тестового подключения

Все действия ниже владелец выполняет под своим Google-аккаунтом. Сам helper не
создаёт проект, не меняет настройки Cloud и не даёт согласие вместо владельца.

1. Откройте [Google Cloud Console](https://console.cloud.google.com/).
   В переключателе проектов выберите **New project / Создать проект**, задайте
   имя `CU Clubs test` и после создания выберите именно его.
2. Откройте **APIs & Services → Library**, найдите **Google Sheets API**, нажмите
   **Enable / Включить**. Для проверки известной тестовой книги достаточно Sheets
   API: Drive API и Drive scopes сейчас не требуются. В старом access-checklist
   упомянуты оба API — это более широкий первоначальный список, а не требование
   текущего helper.
3. В **Google Auth Platform → Branding** нажмите **Get started**, если это новый
   проект. Имя приложения — `CU Clubs test`; support email и contact email — ваш
   доступный адрес. Проверьте данные и завершите создание конфигурации.
4. В **Audience** выберите **External** и оставьте приложение в **Testing**.
   Добавьте свой личный адрес в **Test users → Add users → Save**. Входить при
   авторизации нужно этим же аккаунтом. **Internal** предназначен для аккаунтов
   организации Google Workspace и для личного Gmail здесь не подходит.
5. В **Data Access → Add or Remove Scopes** добавьте только
   `https://www.googleapis.com/auth/spreadsheets`, затем сохраните. Этот scope
   позволяет работать с таблицами, доступными аккаунту, и не ограничен одной
   тестовой копией. Поэтому в настройке бота отдельно закреплён её ID. Проверка
   подключения читает только метаданные, дальнейшая запись требует отдельной
   проверки шаблона. Scope записи нужен будущему календарному адаптеру; Gmail,
   Calendar и полный Drive scope не запрашиваются.
6. В **Clients → Create client** выберите тип **Desktop app**, имя, например
   `CU Clubs local setup`, затем **Create** и скачайте JSON. Нужен именно Desktop
   client, не Web application, API key или service-account key.
7. Сохраните JSON как `google-client.json` **за пределами всех Git-репозиториев**,
   например в `~/.config/cu-clubs/`. Ограничьте доступ к папке владельцем.

Источники: [включение API и Desktop client](https://developers.google.com/workspace/sheets/api/quickstart/python),
[Branding, Audience, test users и scopes](https://developers.google.com/workspace/guides/configure-oauth-consent),
[типы аудиторий](https://developers.google.com/identity/protocols/oauth2/production-readiness/overview).

## 4. Локальная авторизация владельцем

Запускайте на своём компьютере с браузером, из каталога проекта:

```sh
mkdir -p ~/.config/cu-clubs
chmod 700 ~/.config/cu-clubs
chmod 600 ~/.config/cu-clubs/google-client.json
uv run python -m cu_clubs.integrations.google_oauth authorize \
  --client-file ~/.config/cu-clubs/google-client.json \
  --credentials-file ~/.config/cu-clubs/google-user.json
```

Браузер откроет официальный Google consent. Проверьте название созданного
приложения, аккаунт и запрашиваемое разрешение таблиц. Подтвердите доступ сами.
Если появляется предупреждение о непроверенном приложении, продолжать допустимо
только после проверки, что это ваш собственный тестовый проект. При блокировке
или неожиданном приложении остановитесь и проверьте client JSON и test user.

Локальный одноразовый listener слушает только `127.0.0.1` на случайном порту,
проверяет `state`, использует PKCE S256, ждёт не больше 180 секунд и закрывается.
Код обменивается по HTTPS, запрашивается offline-доступ. При успехе сохраняется
refresh token, client ID/secret и scope в `google-user.json` с правами `600`;
токены не печатаются. Короткоживущий access token на диск не сохраняется.
Повторная авторизация заменяет credentials в указанном файле только после успеха.

Источник: [Desktop OAuth, loopback и PKCE](https://developers.google.com/identity/protocols/oauth2/native-app).

## 5. Проверка тестовой книги

В локальном `.env` задайте абсолютный путь вместо примерного:

```dotenv
CU_CLUBS_GOOGLE_AUTH_MODE=oauth
CU_CLUBS_GOOGLE_CREDENTIALS_PATH=/absolute/private/path/google-user.json
```

`CU_CLUBS_GOOGLE_SPREADSHEET_ID` уже должен указывать на созданную тестовую копию.
Не заменяйте его ID рабочей книги. Аккаунт, которым дано согласие, должен иметь
доступ к тестовой копии. Проверьте это открытием копии в браузере под ним.

```sh
uv run python -m cu_clubs.integrations.google_oauth check
```

Команда обновляет access token и делает один read-only запрос метаданных Sheets.
Успех подтверждает доступ на чтение, а не возможность записи и не сохранность
формул, заметок и оформления. В рабочий календарь ничего не записывается.
При ошибке проверьте выбранный Cloud project, включение Sheets API, test user,
доступ аккаунта и путь credentials. `invalid_grant` требует повторной авторизации.

При переносе на сервер закрыто перенесите `google-user.json` в каталог секретов
вне Git и задайте новый абсолютный путь; права файла — `600`, папки — `700`.
Не помещайте файл в image, общие архивы, логи или обычные резервные копии проекта.
Отозвать доступ можно в [настройках подключений Google](https://myaccount.google.com/connections).

## 6. Ограничение Testing: семь дней

Для **External + Testing** refresh token с Sheets scope истекает через **7 дней**.
После этого потребуется снова выполнить `authorize` и заменить закрытый файл
на сервере. Это подходит для проверки, но не обеспечивает автономную постоянную
работу. Токены также могут быть отозваны самим владельцем или Google.

Не переключайте приложение в Production автоматически ради обхода срока.
До постоянного запуска отдельно выбираем устойчивый вариант и проверяем
применимые требования Google, права интеграционного аккаунта и нужные scopes.
Личное использование само по себе не отменяет ограничение Testing.

Источник: [официальное правило срока refresh token](https://developers.google.com/identity/protocols/oauth2#expiration).
