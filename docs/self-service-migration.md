## Целевой контракт из репозитория

`deploy/self-service-project.yaml` — шаблон регистрации, **не live inventory**:
проект `cu-clubs-bot`, test/xgrm, `api`, одна реплика `Recreate`, `/data` 4 GiB,
образ `git.cu3rd.ru/jedi_kitten/cu-clubs-bot`, запрос ingress `clubs-api.cu3rd.ru`.
До проверки DNS/TLS и приёмки этот адрес не выдаётся как рабочий API.

Сборка: `docker build --target selfservice ...`. Runtime API/worker используют
`app` UID/GID10001; обычный Docker target сохраняет прежнего системного
пользователя. Managed `DATABASE_URL` преобразуется в `postgresql+psycopg://`;
`CU_CLUBS_SELF_SERVICE_POOLER=true` включает настройки transaction PgBouncer.
`deploy/selfservice.py` выполняет migrate, запускает API, опциональные worker и
sshd; автоматического bootstrap/назначения ролей/настройки Telegram нет.

SSH внутри контейнера — порт 2222; исторически запрошенный шлюз:
`ssh -p 8222 cu-clubs-test@ssh.cu3rd.ru`. Работа входа на целевой площадке заново
не принята. `deploy/sshd_config` запрещает root, пароли и forwarding.
Обычная HTTP probe проверяет API/БД; supervisor замечает завершение дочернего
процесса, но не зависший worker. Heartbeat и очередь проверять отдельно.

## Передача закрытых настроек

Сохранить прежний verification secret дословно, Telegram credentials, Google
OAuth credentials/права на тестовую книгу, numeric получателя backup и историю
backup-файлов. `/data/runtime-env.json` содержит закрытые runtime-настройки;
`/data/google-credentials.json` и SSH host key также приватны. Они не входят
в PostgreSQL dump и не публикуются вместе с документацией.

Шаблон проекта содержит mappings Telegram/verification/Google/backup, но **не**
Yandex OAuth. Для входа через Яндекс нужны отдельные изменения регистрации
проекта и sealed delivery: secret `CU_CLUBS_YANDEX_CLIENT_SECRET`, variables
`CU_CLUBS_YANDEX_AUTH_ENABLED`, `CU_CLUBS_YANDEX_CLIENT_ID`,
`CU_CLUBS_YANDEX_REDIRECT_URI`. Tag-only helper этого не добавляет.
Перенос callback на другой хост требует регистрации точного нового URI у Яндекса;
не менять текущий рабочий callback до готовности новой среды.

SMTP не подключён и для Яндекс-входа не требуется. Старые записи про ввод логина
без почты ниже описывают прежние выпуски и не подменяют текущую проверку Яндекса.
Sealed secrets создаются штатно для namespace/Secret платформы; plain values
не передавать через PR, Actions logs или открытые env. Настройка доставки —
[selfservice-delivery.md](selfservice-delivery.md).

## Порядок будущего переключения

1. Получить доступ к платформе, заново прочитать её регистрацию/delivery/статус,
   восстановить доставку актуального исходного commit. Проверить образ, UID,
   сертификат, SSH, managed PostgreSQL и совместимость настроек. До переключения
   worker=false, внешние интеграции пробной копии выключены.
2. Проверить восстановление отдельной копии и полную сверку схемы/таблиц.
   Согласовать окно, возврат и допустимую остановку API/бота.
3. Остановить **оба** старых API/worker и исключить их автоматический restart
   во время финального снимка. Сохранить старые тома, конфигурацию и образ.
   Сделать финальный custom dump; отдельно сохранить backup-файлы и credentials.
4. Перенести снимок на цель. При worker=false выполнить
   `python /app/deploy/ops.py restore /data/final.dump`, затем
   `python /app/deploy/ops.py migrate`. Restore применяет `--single-transaction`,
   `--no-owner --no-acl --clean --if-exists` к уже выбранной БД; он разрушительно
   заменяет данные **целевой** БД и не должен указывать на источник.
5. Сверить все прикладные таблицы, revision, контрольные данные и backup-файлы
   без публикации персональных данных. Проверить Google credentials, OAuth
   redirect, отсутствие сторонних отправок и доступ API с нужным consent.
6. Отдельной доставкой включить один worker; проверить heartbeat, единственный
   poller, очереди, Telegram навигацию, календарь, backup и реальные OAuth flows.
   Опубликовать адрес REST API только после проверки его HTTPS и полномочий.
7. Записать результат cutover и приёмки в handover/project-status и API guide.
   Старые контейнеры оставить остановленными, данные не удалять.

До новых записей откат — выключить цель и запустить сохранённый источник.
После новых записей сначала перенести свежие данные обратно и проверить схему:
возвращать устаревшую БД нельзя. Регистрация проекта, опубликованный image,
готовность pod, restore, сверка и cutover — самостоятельные этапы.

## Повтор переноса после готовности платформы

15 ноября source run №6 прошёл 397 тестов, lint/format и проверку 25 API-маршрутов.
Образ `4815914cf6af2a5800b7a0b384055139fa260387` собран
(`sha256:d8a147113541b7021916a52cbb6ca694e89cf951ddfaa9990d853159e5ce076f`),
но загрузка временным job token завершилась `unauthorized: reqPackageAccess`.
Владелец разрешил создание `cu-clubs-registry-publisher`: `write:package` /
Public only, без доступа к коду и аккаунту. Ключ создан и сохранён только
в Actions Secret `REGISTRY_TOKEN` CU Clubs; source run №6 запущен повторно.
Права Forgejo на пакеты не ограничиваются одним пакетом, что согласовано
владельцем; само значение не хранится в исходниках или документации.

[PR №206](https://git.cu3rd.ru/cu3rd/self-service/pulls/206) меняет только tag
проверенного приложения; `SELF_SERVICE_WORKER_ENABLED=false`, mappings и
шифрованные настройки сохраняются. Валидатор платформы прошёл для 19 проектов
и всех доставок. До публикации образа и принятия PR перенос не завершён.

Повтор run №6 остановился до тестов при установке wheel: `No space left on
device` на CI-раннере. В workflow очищаются списки apt и download-cache pip;
uv-cache перенесён на один том с `.venv` с hardlink, чтобы не хранить вторую
копию каждого установленного пакета. Это изменение только сборки; результат
первой полной проверки 397 тестов сохраняется как отдельное свидетельство,
но успешная публикация нового выпуска ещё обязательна.

Диагностика run №8 подтвердила причину повторных ошибок: PostgreSQL
`PANIC: could not write to file pg_wal/...: No space left on device`;
перед тестами было 126 MiB свободно, при остановке — 14 MiB. Для одноразовой
CI-базы ограничены WAL 32–64 MiB и интервал checkpoint 30s, включено сжатие WAL;
обычные fsync и durability сохранены. После установки очищается uv-cache,
hardlink-файлы окружения остаются доступны. Рабочая БД и target-конфигурация
этими настройками не изменяются. Публикация ещё не подтверждена.
