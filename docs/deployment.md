## Что сохранить и передать

- Два действующих Compose-файла, точный image ID/тег и предыдущий рабочий образ.
  Серверный release overlay отсутствует в текущем checkout: получить его у
  владельца развёртывания перед воспроизведением или обновлением.
- Закрытый серверный `.env` с правами `600`, неизменный
  `CU_CLUBS_VERIFICATION_SECRET`, OAuth и Telegram credentials. Значения
  передаются отдельно от Git и открытой документации.
- Тома `database`, `backups`, `google_credentials`. Google credentials находятся
  по `/run/cu-clubs-secrets/google-user.json`, не входят в PostgreSQL dump.
- Разрешённые proxy routes и требования к скрытию query OAuth в журнале.
  Общий Caddy обслуживает другие проекты; менять его только в согласованных границах.

Смена verification secret при обычном обновлении/восстановлении ломает чтение
зашифрованных данных и подписи. Перед сменой образа проверить UID/GID пользователя
`app` и владельцев существующих томов: стандартный runtime и selfservice имеют
разные настройки пользователя. Не переносить тома с произвольным `chown`.

## Безопасная проверка на действующем сервере

Из `/home/kir/cu-clubs-bot` использовать **оба** файла:

```sh
dc() { docker compose -p cu-clubs-test -f compose.server.yaml -f compose.release-20261116.yaml "$@"; }
dc config --quiet
dc ps
curl --fail --silent --show-error http://127.0.0.1:8310/health/ready
dc exec -T worker python -c 'import os,time; assert time.time()-os.path.getmtime("/tmp/cu-clubs-worker-heartbeat") < 240; print("worker heartbeat fresh")'
```

Не выводить полный `docker compose config`, environment из inspect, `.env`,
credentials, URL БД и OAuth query. Проверки выше не отправляют тестовые сообщения.
Успешный health не подтверждает доступ к Google, SMTP, университетскому SSO
или корректность восстановления dump.

## Воспроизведение образа из точного Git snapshot

Собрать из чистого временного контекста проверенного commit, а не из каталога,
где могут находиться `.env`, `.cache`, dump или чужие незакоммиченные изменения:

```sh
release_commit=$(git rev-parse HEAD)
release_context=$(mktemp -d)
git archive "$release_commit" | tar -x -C "$release_context"
docker build --target default -t "cu-clubs-local:$release_commit" "$release_context"
```

Перед сборкой убедиться, что HEAD — именно согласованный выпуск. `git archive`
исключает незакоммиченные файлы: нужное исправление сначала включается в
проверенный commit. Dockerfile использует `uv.lock` и `uv sync --frozen`.
После сборки сверить UID/GID `app` с текущими `999:999`, ресурсы, миграции и
хеши модулей. Нельзя утверждать побайтную воспроизводимость всего image:
базовые images не закреплены digest, apt также зависит от репозитория пакетов.

Сохранённый серверный overlay должен явно указывать новый проверенный тег,
не менять `.env`, volume mounts и остальные runtime-параметры. Этот файл не
генерируется командами выше. Не заменять его догадкой по отсутствующему файлу
в checkout. Старый образ и overlay сохранить для возврата.

## Обновление и откат на прежнем сервере

1. Зафиксировать текущий образ/overlay, schema revision и состояние очередей.
   Сохранить свежую резервную копию; отдельно сохранить закрытые настройки и Google
   credentials. Проверить восстановление в изолированной БД.
2. Подготовить проверенный пакет исходников/образ с неизменяемым тегом. Согласовать
   release overlay: запуск одного `compose.server.yaml` может собрать другой образ.
3. Выполнить миграции нужным образом, затем пересоздать только API/worker проекта
   `cu-clubs-test` с обоими файлами. Повторный bootstrap не является шагом обычного
   обновления. Тома и сервисы других проектов не трогать; `down -v` не использовать.
4. Проверить ready, heartbeat, image ID и хеши затронутых модулей, сохранность
   настроек. Проверить необходимые пользовательские сценарии отдельно.
5. При откате вернуть сохранённый overlay/образ. Если миграции либо новые записи
   несовместимы с прежним кодом, сначала определить безопасный план возврата БД;
   не запускать старую копию поверх неподходящей схемы и не терять новые данные.

`deploy/server-up.sh` — helper первоначального запуска **только базового** Compose:
он делает build, migrate и bootstrap. Он не учитывает release overlay, поэтому
не служит командой обновления действующего экземпляра.

## Резервные копии и восстановление

Worker создаёт PostgreSQL custom dump по `CU_CLUBS_BACKUP_CRON` в настроенной
таймзоне (по умолчанию ежедневно 03:00 Europe/Moscow), затем задачу `backup.ready`.
Доставка разрешена только настроенному numeric получателю; файл больше 49 MiB
адаптер не отправляет. Успех dump и `outbox.status=sent` — разные этапы.
Автоматического удаления файлов нет. Полученный backup остаётся в Telegram:
следующая навигация переносит экран под него, а не удаляет документ.

`deploy/restore-check.sh` создаёт временную БД, восстанавливает последний dump,
показывает три контрольных счётчика и удаляет свою БД. Он использует только
базовый Compose-файл; перед применением на действующем сервере адаптировать вызов
к обоим файлам без изменения секретов. Проверка не запускает worker для копии.
Она не заменяет полную сверку таблиц, схемы и нужных прикладных данных.
Никогда не восстанавливать пробную копию в рабочую БД.

## Первоначальная установка нового отдельного экземпляра

Это не инструкция замены действующего. База — `compose.server.yaml`,
`.env.example`, `src/cu_clubs/config.py`; Yandex-переменные также описаны
в [yandex-login.md](yandex-login.md). Шаблонные пустые значения не включают вход.
Задать свои закрытые credentials и numeric IDs, сохранить `.env` с правами 600.
До подключения выбранного бота оставить внешнюю доставку выключенной.
Сначала build и db, затем migrate, однократный bootstrap по решению владельца,
затем API/worker. `bootstrap` создаёт начальные роли и клуб: не переносить этот
шаг на восстановленную среду как автоматическую процедуру.

## Google и переключение Telegram transport

Google OAuth устанавливается через `deploy/install_google_credentials.py`:
authorized-user JSON поступает в stdin, каталог `700`, файл `600`, владелец `app`.
Установщик запускается от root только в собственном контейнере с нужным томом.
Проверка `python -m cu_clubs.integrations.google_oauth check` выполняется от `app`
и читает метаданные. Для записи дополнительно нужны календарные флаги и точное
совпадение ID тестовой книги. Подробности — [integrations-setup.md](integrations-setup.md).

Текущий polling не переключён на webhook. Для будущего перехода отдельно открыть
HTTPS route, задать transport/webhook URL/секрет, остановить старый polling,
выполнить `cu-clubs webhook`, затем включить единственный worker. Pending updates
не сбрасываются. Само наличие публичного OAuth callback не публикует webhook.
Восстановленная тестовая среда использует `external_delivery_enabled=false`.
