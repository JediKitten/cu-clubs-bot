# Независимая проверка безопасности API — 14 ноября 2026

## Область

Проверены `api.py`, `api_service.py`, `api_models.py`, `api_security.py`,
`api_delivery.py`, `api_ui.py` и миграция `20261114_0009_api.py` относительно

исходников выполнял автор API после сообщений о найденных проблемах.

Проверка ограничена доступом к клубам и личным данным, согласиями пользователей,
идемпотентностью, конкуренцией за место, порядком курсора и доставкой webhook.

## Найденные и исправленные проблемы

1. **P1 — клубный ключ читал личную запись своего владельца.** GET встречи
   передавал `issuer_telegram_id` в персонализированный DTO даже без пользовательского
   токена. Если лидер был записан, ответ содержал `registered`, `registered_at` и
   закрытый текст после записи. Автор убрал неявную персонализацию: actor по
   умолчанию отсутствует; личные поля требуют подтверждённого пользовательского
   токена. Регрессия `test_event_read_key_does_not_impersonate_issuer` воспроизвела
   проблему до исправления и прошла после него.
2. **P1 — согласие пользователя обходило границу клуба при чтении открытой встречи.**
   Ключ клуба A с пользовательским токеном мог получить личную запись студента и
   текст после записи встречи клуба B. Открытость карточки не разрешает чтение
   этих личных данных. Автор добавил проверку принадлежности встречи клубу клиента
   перед персонализацией. Регрессия
   `test_delegation_cannot_expose_another_clubs_personal_event_data` сначала
   подтвердила раскрытие, затем получила безопасный результат после исправления.

## Подтверждённые проверки

Финальный целевой прогон `tests/test_api_security.py` и
`tests/test_api_delivery.py`: **22 passed за 5,91 с**, без пропусков. Ruff прошёл.
Одна предупреждающая запись Starlette относится к используемому TestClient и
не означает ошибку сценария.

Проверены:

- Чужая закрытая встреча недоступна ключу своего клуба даже при issuer-администраторе;
  изменение, отметка и чтение ведомости отвергаются. Личные данные чужой открытой
  встречи также недоступны через пользовательский токен.
- Ключ и введённый Telegram ID не заменяют согласие. Привязка проверяет клиента,
  пользователя, подтверждение, срок действия и однократный обмен; отзыв токена
  действует на следующем запросе.
- Повтор одинаковой операции с тем же ключом возвращает прежний ответ; другое тело
  даёт 409. Устаревший If-Match даёт 412. Повтор успешного запроса с прежним If-Match
  возвращает сохранённый ответ. Ответ обмена токена хранится зашифрованным.
- Конкурентная регистрация через API и Telegram-домен оставляет ровно одну активную
  запись при одном свободном месте.
- Отдельные PostgreSQL-транзакции подтверждают: более высокий курсор не обгоняет
  незафиксированное предыдущее изменение.
- Закрытые и смешанные DNS-адреса отвергаются; отправка использует проверенный
  публичный IP, исходные Host и TLS SNI, без прокси окружения и перехода по redirect.
- HMAC проверяется на исходных байтах с timestamp. Повтор после неопределённого
  сетевого исхода сохраняет delivery_id; приёмник может исключить повторный эффект.
  Отозванные endpoint и клиент не доходят до транспорта. Feed не содержит ключей,
  секретов webhook или текста после записи.
- Составные первичные ключи идемпотентности и лимитов запросов, уникальность активных
  grant/endpoint и delivery проверены по миграции; миграции применялись в тестах.

## Границы результата

Это ограниченное ревью исходников и автоматизированных сценариев, **не пентест**
и не доказательство отсутствия всех уязвимостей. Использованы отдельные схемы
одноразового локального PostgreSQL и синтетические люди, клубы и события.
HTTP API проверялся через TestClient внутри процесса. DNS и исходящий HTTP
webhook заменялись контролируемыми реализациями; настоящие TLS-соединения,
публичная сеть, DNS-провайдеры, reverse proxy и внешний приёмник не проверялись.
Сервер, рабочие credentials и реальные данные участников не читались.

Допуск относится к перечисленным сценариям и состоянию исправлений на момент
прогона. Он не подтверждает эксплуатационную настройку, общий релизный прогон
или последующие изменения API. Коммит и публикация проверяющим не выполнялись.

## Дополнительная проверка рабочих сценариев

После основного ревью добавлены `tests/test_api_workflow.py` и независимый пример
`examples/club_api_client.py`. Целевой прогон: **4 passed за 3,76 с**; Ruff прошёл,
CLI `--help` запускается без настроек и сетевых обращений.

Проверены HTTP-создание, чтение, изменение черновика и опубликованной встречи,
публикация, пользовательская запись и отмена, отмена встречи, приглашение партнёра
с отдельным личным подтверждением лидера, получение изменений. Multipart XLSX
предпросмотр сохраняет batch, но не создаёт людей или посещения; подтверждение
один раз и повторы с прежним либо новым ключом оставляют одно посещение.
Проверены базовые OpenAPI paths, bearer security, входная схема привязки,
multipart и фактические заголовки Cache-Control/X-Request-ID. Полнота всех схем
ответов и новой метаинформации заголовков этим прогоном не утверждается.

Пример клиента проверен через MockTransport: пути, Authorization,
Idempotency-Key, If-Match и отдельный X-User-Token. Проверка подписи принимает
исходное тело, использует constant-time сравнение и отвергает изменения тела,
неверный секрет и timestamp за пределами ±300 секунд. Подпись не заменяет
устойчивое исключение повторов по delivery_id на стороне принимающего сервиса.
