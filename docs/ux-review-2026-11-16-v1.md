# UX review: v1 digest outputs and remaining routes — 16 November 2026

## Scope and status

This review translates the owner's 16 November direction into concrete UX
changes and acceptance criteria. A digest must produce two usable results:

1. A Telegram-ready text post following the supplied sample: bold weekday
   headings, arrow links to the relevant club or collaboration, a `P.S.` and
   `#Дайджестсобытий`.
2. Editable digest cards made through the Figma workflow.

The inspected source currently exports JSON for Figma only. The bot flow and
plugin are source-reviewed, not live-accepted. The final implementation diff is
pending; this document is a proposal/checklist, not a claim that the two outputs
are implemented. Preserve the supplied sample's exact copy and order when it is
available to the implementing agent.

## Proposed Telegram route

Keep one Telegram message as the active work surface. After choosing a week and
all events or a manual selection, show one shared digest preview with the week,
selected event count, and the complete Telegram post text in its final format.
The preview should make the two output actions explicit and distinct:

- **Скачать текст поста** — a plain text/HTML artifact ready to paste into the
  Telegram channel; do not imply that it publishes the post.
- **Подготовить карточки в Figma** — the JSON file required by the existing
  Figma plugin, with a short instruction to open the plugin and create the card
  copy.

Keep **Изменить выбор**, **Изменить неделю**, and **Отмена** available from the
preview/output screen. Back from manual selection returns to the all/manual
choice for the same week; returning from preview preserves week and all checked
events. Changing the week clears the old selection and makes that consequence
clear. Any detected event change returns to a refreshed preview for review;
neither output should be silently generated from stale data.

The post preview must visibly distinguish each weekday heading in bold and
preserve the sample's line breaks, arrow-link pattern, `P.S.` and exact hashtag
`#Дайджестсобытий`. Every arrow points to the relevant club or, for a
collaboration, the single relevant collaboration/event destination. No
placeholder, raw URL, or missing-link arrow may pass as a ready post. If a
selected event has no valid public destination, explain it and provide a direct
way to edit the selection.

## Figma route

Keep the current single-panel plugin workflow: choose source frames, load the
JSON, check, create/update a copy. Make the result named as the card output and
keep its scope clear: it creates editable Figma cards; it does not publish the
Telegram text. If the check fails, retain the loaded file and selected frames
when possible, show the specific correction, and allow checking again without
restarting. A successful run must leave the source frames intact and report the
created page count. Re-running on the plugin-created section updates that copy
only after a successful build.

## Calendar, history, ICS and responsible contact

The calendar batch should keep the user's current week and club filter visible
through the route. In particular, the **По клубам** chooser should show the
week/date range (and current club filter when one is active), so a paginated
club list remains understandable. The week screen should offer **Все клубы**
when filtered; changing to an adjacent week keeps the same club filter. The
club chooser's back action returns to that week/filter, and opening a meeting
then returning from its card restores the same filtered week.

The personal list has explicit **Предстоящие** and **История** sections. Opening
a card and using Back returns to the same section/list. **Экспорт в календарь**
delivers an `.ics` attachment as a separate action; its return button goes back
to the event card, preserving whether it was opened through an authorized link.
The contact field is optional, shown at the end of event creation and in
**Участники и доступ** for edits. Its prompt must say the contact is visible to
everyone who can view the event and invite only information safe to publish;
the same value can be saved, edited, cleared, and retained by a template.

Calendar/contact acceptance: verify week bounds and pagination, no closed or
draft events in public club filters, collaboration partners appear as filter
options, adjacent-week navigation preserves the filter, **Все клубы** clears
it, card Back restores the selected week/filter, history toggles preserve the
section, ICS downloads and returns to the card, and contact add/skip/edit/clear
round-trips through event creation and templates.

## FAQ routes

The main FAQ opens three clear sections: clubs, club levels and using the bot.
Each question shows a specific answer, one relevant next action when useful,
and a handbook link. Keep the current registration mode reflected in the bot
FAQ. When opened from one club's level button, show only that assigned level;
Back returns to the same club card. From a contextual FAQ section, Back from an
answer should return to the question list, and Back from that list should return
to the originating bot screen. A stale callback from a contextual level screen
must not reveal the full levels list.

FAQ acceptance: verify the main menu → section → question → related action path,
Back to question list and section menu, source-specific registration guidance,
club-level context/return, handbook URL on each screen, and stale callbacks
cannot escape their context. Handbook-derived answers stay marked unavailable
until the source has actually been verified.

## Acceptance criteria for final diff

- The admin sees two separately named results for the selected digest: a
  Telegram-ready text post and Figma card data. The Figma JSON is not presented
  as the Telegram post, and neither action implies channel publication.
- The shared preview exposes the whole post, selected week/count and the
  separate card route. It follows the provided sample's content structure:
  bold weekday headings, arrow links, `P.S.` and `#Дайджестсобытий`.
- Post links resolve to the appropriate club/collaboration and event; absent or
  invalid targets are reported before export. Collaborations are represented
  once and link to the appropriate shared destination.
- Manual selection pagination preserves every checked event. Back from
  selection returns to the choice screen; back from preview/output returns to
  selection with the same week and checks. Week changes explicitly reset the
  selection. Cancel exits without generating either output.
- Refresh/version checks apply to both outputs. Changed, removed, or newly
  eligible records are shown in a refreshed preview and require another
  deliberate export.
- Empty weeks and selection-limit errors give a clear recovery action and retain
  useful context. No empty or truncated artifact is offered as complete.
- There is one active Telegram screen/message per flow. Old UI and generated
  files are removed according to the existing window lifetime policy when
  navigation replaces them; the currently useful output remains accessible
  until then. Replacing an output does not leave duplicate obsolete attachments.
- The Figma plugin remains one-screen, preserves the chosen file/settings and
  source selection on recoverable errors, and communicates “create cards” and
  “update this copy” distinctly. It never suggests that it generated or sent the
  Telegram post.
- Acceptance covers every parent/back/cancel route, file cleanup, pagination,
  repeated output generation, event-change recovery, and a collaboration case.
  Source review is separate from live Telegram and visual Figma acceptance.

## Initial source review before the final diff

- `src/cu_clubs/digest_ui.py` currently offers one export action,
  **«Скачать JSON для Figma»**. The preview lists event time/title, not the
  sample-shaped Telegram post. The two required results therefore are not yet
  visible in the inspected flow.
- Week choice, manual/all choice, paginated checked items, preview, cancel, and
  same-week selection retention are already represented in the source. Preserve
  those behaviors while adding the second output; do not create a parallel
  wizard that loses selection state.
- `figma/digest/ui.html` has one panel and separate check/create actions. Its
  source copy explains the Figma result, but should call it the card result and
  continue to make clear that the source stays intact.
- Existing upload instructions are adequate as a basic linear path. The final
  acceptance should specifically try bad input followed by correction, a
  second run, and updating a previously created plugin section.

## Final source re-review — 16 November 2026

The final digest source now has two distinct output paths from the same
version-checked selection. The rendered post has bold weekday headings, linked
club labels, one shared event link for a collaboration, linked P.S., and the
requested hashtag. Long posts retain event links across numbered parts; the
complete post is available as an HTML file. The Figma JSON has a separate
button and explicit instructions, and does not claim to publish to the
channel. Post preview, page navigation, file download, and cards revalidate the
same selected snapshot. When it has changed, the flow returns to a refreshed
selection preview and asks for another action. Selection, week, back, cancel,
and file cleanup behavior is consistent with the prior checklist.

The link destination is the event card. A collaboration is a single card that
shows both clubs; this interpretation is recorded here because the owner
direction asked for arrows to clubs/collaborations. If the supplied sample
instead points to standalone club profiles, that target should be confirmed
against the sample before a live post is accepted.

The FAQ helper is wired into the Telegram dispatcher before other flows. The
main menu, question lists, contextual level screen, handbook links, dynamic
registration guidance, and Back paths are source-reviewed. A contextual level
screen shows only the assigned level; a contextual answer returns to its
question list, then to the original screen. The handbook text is attributed to
the verified source and keeps variable reach threshold X explicit.

Root reports 26 PostgreSQL/digest tests passed, plus an additional four-test
rerun, and the calendar/FAQ owner reports 71 FAQ-related tests passed. These
are automated checks, not live Telegram acceptance or visual Figma acceptance.
Those two manual checks remain open.
