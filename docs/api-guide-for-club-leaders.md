# Инструкция по API для лидеров клубов с внешними ботами

Проверено **14 ноября 2026** по реализации `d07e016`, API `/api/v1`.
Это основная пошаговая инструкция лидера и разработчика клубного бота.
Она обновляется в репозитории вместе с API. Краткий технический контракт и
полный список методов — [api-integration.md](api-integration.md).
Состояние проекта — [project-status.md](project-status.md).

## 1. Что можно подключить прямо сейчас

Внешний бот может показывать открытые встречи, создавать и менять встречи своего
клуба, предлагать коллаборации, записывать согласившихся студентов, отмечать
посещение студентов, получать ведомости и отслеживать изменения. База общая
с университетским ботом: последнее место нельзя занять дважды через разные интерфейсы.

Лидер выдаёт ключ подключения, разработчик настраивает сервер своего бота,
студент отдельно разрешает персональные действия. Ключ клуба не заменяет согласие.

Текущие ограничения:

- Используем тестовый [@cu_clubs_app](https://t.me/cu_clubs_app).
- **Публичного HTTPS-адреса API пока нет.** API слушает `127.0.0.1:8310`
  на сервере. Доступ извне — через SSH-туннель для уполномоченного разработчика.
  Если у команды нет доступа к серверу, сначала согласуйте подключение с администрацией.
- Для персональной записи нужна настоящая проверка студенческой почты.
  Почтовый отправитель отложен: путь нового студента пока нельзя пройти целиком.
  Тестовое назначение лидера без почты не подтверждает его студенческий профиль.
- API пока не управляет шаблонами, анкетами, аналитическими отчётами, профилем
  и ролями клуба, выдачей QR. Внешний гость проходит QR-путь в университетском боте.
- Приглашение партнёра можно отправить через API, но принимает его лидер
  партнёра лично в университетском боте.

## 2. Лидеру: выдать ключ

1. Открой университетского бота под аккаунтом лидера.
2. Перейди в **«Мои клубы → нужный клуб → Настройки клуба → Интеграции»**.
3. Нажми **«Создать ключ»** и введи название, например «Бот киноклуба».
4. Выбери права и подтверди выдачу:

   | Набор | Что разрешает |
   |---|---|
   | Только чтение | Карточки, календарь и изменения: `events:read`, `changes:read` |
   | Полный доступ клуба | Все шесть прав из раздела 5, включая ведомости и отметки; личная запись всё равно требует согласия студента |

5. Бот пришлёт `cu-clubs-api-key.txt`. В файле находятся `API_KEY`, `CLUB_ID`,
   `SCOPES`. Повторно посмотреть полный ключ в карточке нельзя.
6. Передай разработчику инструкцию, идентификатор клуба и ключ через закрытый
   канал. Разработчик сохраняет ключ в хранилище секретов сервера своего бота.
   Токен Telegram-бота CU Clubs ему не нужен.

Выдавай отдельный ключ на приложение и окружение. Сейчас права существующего
ключа не редактируются: для изменения создай новое подключение.
Ключи не помещай в Git, общие чаты, скриншоты и журналы запросов.

Для отзыва открой **«Интеграции → подключение → Отозвать ключ»**.
Следующее обращение старого подключения отклоняется; его персональные токены
не дают обходного доступа. Текущие полномочия выдавшего ключ также проверяются.
При смене лидера согласуй перевыпуск подключений. При утечке сразу отзови ключ,
создай новый и заново привяжи студентов к новому подключению.

## 3. Разработчику: адрес и первый запрос

Нужны ключ, `CLUB_ID` из файла, адрес API и доступ к серверу своего бота.
Для записи потребуется подтверждённый студент, для webhooks — свой HTTPS-получатель.

Сейчас администратор может организовать туннель:

```sh
ssh -N -L 8310:127.0.0.1:8310 kir@87.120.84.226
```

Пока соединение открыто, на компьютере разработчика доступны:

| Назначение | Адрес |
|---|---|
| Адрес для готового клиента | `http://127.0.0.1:8310` |
| REST API | `http://127.0.0.1:8310/api/v1` |
| Интерактивные схемы | `http://127.0.0.1:8310/docs` |
| OpenAPI JSON | `http://127.0.0.1:8310/openapi.json` |

В контейнере внешнего бота `127.0.0.1` означает сам контейнер, а не соседний сервис.
Адрес согласует администратор; не открывай API наружу без HTTPS.
Адрес webhook-получателя твоего бота отличается от адреса API CU Clubs.

Есть [готовый Python-клиент](../examples/club_api_client.py): нужны Python 3.12
и `httpx`, в окружении проекта зависимости уже установлены.
Загрузи `CU_CLUBS_API_KEY` из хранилища секретов в переменную окружения.
`CU_CLUBS_API_URL` для туннеля — `http://127.0.0.1:8310`.
Ключ не передавай аргументом командной строки.

Первая проверка из корня репозитория, без записи данных:

```python
import os
from examples.club_api_client import ClubApiClient

with ClubApiClient(os.environ["CU_CLUBS_API_URL"], os.environ["CU_CLUBS_API_KEY"]) as api:
    club = api.request("GET", "clubs/" + os.environ["CU_CLUBS_CLUB_ID"])
    print(club["name"])
```

`CU_CLUBS_CLUB_ID` установи из `CLUB_ID` файла. Это публичный ID клуба, не название
и не Telegram-тег. ID встречи бери из поля `id` ответа.

## 4. Обязательные правила запросов

| Правило | Как применять |
|---|---|
| Авторизация | Всегда `Authorization: Bearer <API_KEY>` |
| Личные действия | Дополнительно `X-User-Token: <USER_TOKEN>` именно этого студента |
| Формат | JSON UTF-8; даты ISO 8601 с поясом, например `2026-12-01T18:00:00+03:00`; неизвестные поля отвергаются |
| Защита от дублей | Все `POST/PATCH/PUT/DELETE` требуют `Idempotency-Key`: 1–128 печатных ASCII без пробелов |
| Защита от потери правок | Правка встречи, публикация, приглашение и отмена требуют `If-Match: "<version>"` |
| Ограничения | По умолчанию 120 запросов/минуту на ключ; JSON до 256 КБ, XLSX до 10 МБ |

Сохрани ключ операции до отправки. При тайм-ауте повтори **тот же метод, путь,
тело, пользователя и If-Match с прежним ключом**. Успешное действие не выполнится
дважды; `Idempotency-Replayed: true` обозначает повтор ответа.
Для нового действия используй новый ключ. Готовый клиент умеет принимать
`--idempotency-key`; не полагайся на автоматически новый ключ при повторном запуске.

Версия есть в `version` ответа и `ETag` одиночной карточки. После `412` перечитай
встречу, согласуй правку заново и отправь новую операцию с актуальной версией.
Создание и личная запись не требуют `If-Match`.

В списках передавай выданный `next_cursor`. Для обычных списков `null` означает
конец; у `/changes` дополнительно проверяй `has_more` и сохраняй последний курсор
для следующего опроса. Не увеличивай курсор самостоятельно.

## 5. Права и доступ к чужим данным

| Право | Назначение |
|---|---|
| `events:read` | Карточки клубов, открытый календарь, доступные карточки встреч |
| `events:write` | Создание, правка, публикация, приглашение и отмена встреч |
| `registration:self` | Привязка, свой профиль, собственная запись и статус |
| `attendance:write` | Отметка студента и импорт XLSX |
| `roster:read` | Ведомость доступной встречи |
| `changes:read` | Журнал изменений, webhooks и контроль доставки |

Открытый календарь показывает открытые опубликованные встречи разных клубов.
Управление, ведомости и персональные действия ограничены своим клубом и принятыми
коллаборациями. Ключ, выданный администратором, не получает его глобальные права.
Закрытая встреча не попадает в открытый список. Недоступный объект может вернуть
`404`, чтобы не раскрывать его существование.

## 6. Создание, публикация, перенос и коллаборация

После настройки окружения выполни из корня репозитория:

```sh
python examples/club_api_client.py create \
  --title 'Встреча клуба' --description 'Обсудим выбранный фильм' \
  --starts-at '2026-12-01T18:00:00+03:00' \
  --ends-at '2026-12-01T20:00:00+03:00' \
  --capacity 30 --idempotency-key create-december-meeting
```

Ответ `201` содержит `id`, `version`, `status: draft`. Это пока черновик.
Для публикации подставь ID и текущую версию из ответа:

```sh
python examples/club_api_client.py publish EVENT_ID \
  --version CURRENT_VERSION --idempotency-key publish-december-meeting
```

Основные поля `POST /events` и `PATCH /events/{public_id}`:

| Поле | Ограничение |
|---|---|
| `title` / `description` | До 45 / 250 символов |
| `post_registration_text` | Текст после записи, до 150 символов |
| `starts_at`, `ends_at` | Начало и окончание с поясом; окончание позже начала |
| `registration_deadline` | Дедлайн не позже начала |
| `capacity`, `expected_attendance` | Положительное число либо `null` |
| `venue_type` | `campus`, `external`, `online`; по умолчанию `campus` |
| `room`, `venue_details` | Аудитория до 300 символов, детали до 2000 |
| `needs_talk`, `needs_microphones` | `true` / `false` |
| `visibility` | `open` / `closed`; по умолчанию `open` |

Черновик может быть неполным, публикация проверяет обязательные данные.
Для публикации нужны название, описание, начало и конец; для внешней площадки
или онлайна также `venue_details`. Если дедлайн не задан, он становится равен началу.
В `PATCH` передавай только изменяемые поля. При переносе согласуй новые начало,
конец и дедлайн и передай их одной правкой. ID и регистрации сохранятся.
Лимит нельзя уменьшить ниже числа активных регистраций.

Примеры чтения календаря и переноса через тот же `ClubApiClient`:

```python
# api — уже созданный клиент из раздела 3.
page = api.request(
    "GET",
    "events",
    params={
        "from": "2026-12-01T00:00:00+03:00",
        "to": "2027-01-01T00:00:00+03:00",
        "club_id": os.environ["CU_CLUBS_CLUB_ID"],
        "limit": 50,
    },
)
current = api.request("GET", f"events/{event_id}")  # event_id — сохранённый ID
updated = api.request(
    "PATCH",
    f"events/{event_id}",
    version=current["version"],
    idempotency_key="reschedule-december-meeting",
    body={
        "starts_at": "2026-12-02T18:00:00+03:00",
        "ends_at": "2026-12-02T20:00:00+03:00",
        "registration_deadline": "2026-12-02T18:00:00+03:00",
    },
)
```

У календаря обязательны обе границы с часовым поясом; интервал возрастает
и ограничен примерно годом (проверка разницы до 366 дней). Страница встреч —
до 100 элементов; ведомости, изменения и доставки — до 500.
В постоянной интеграции ключ переноса привязывай к сохранённому заданию,
а не используй пример повторно для другой встречи.

Для совместной встречи вместо обычной публикации:

```sh
python examples/club_api_client.py invite EVENT_ID --club PARTNER_CLUB_ID \
  --version CURRENT_VERSION --idempotency-key invite-december-partner
```

Лидер партнёра лично принимает карточку в университетском боте. До согласия
нет опубликованной совместной встречи и записи. Проверяй новый `status`
и `version`; успешный запрос приглашения не означает согласия партнёра.
Для отмены существует отдельный endpoint; история встречи не удаляется.

## 7. Персональная привязка и запись студента

1. Внешний бот получает числовой Telegram ID из сообщения **самого человека**.
   Не доверяй полю, куда вручную ввели чужой ID.
2. Сервер вызывает `POST /links` с `{"telegram_id":123456789}`, ключом клуба
   и новым ключом операции. ID в примере вымышленный: подставь ID отправителя.
3. Ответ `201`: `id`, `verification_uri`, `exchange_code`, `expires_at`, `status`.
   Сохрани его на сервере. Человеку покажи кнопку только с `verification_uri`.
   `exchange_code` не предназначен для пересылки в чат или ручного ввода.
4. Человек открывает университетского бота, при необходимости подтверждает
   почту и отдельно нажимает **«Разрешить подключение»**. Просто открыть ссылку
   или подтвердить почту недостаточно.
5. После возвращения человек нажимает «Я подключил» в своём клубном боте
   (эту кнопку реализует его разработчик). Сервер вызывает
   `POST /links/{link_id}/exchange` с `{"exchange_code":"..."}`.
6. `409 LINK_PENDING` означает, что согласия пока нет. Предложи завершить шаг,
   не запускай бесконечный частый опрос. Ссылка живёт 10 минут; после истечения
   начинай новую привязку.
7. Успешный обмен возвращает `user_token`, `token_type`, `expires_at`.
   Сохрани токен на сервере для этого Telegram ID и этого подключения.
   Срок по умолчанию 90 дней, ориентируйся на `expires_at`. Автоматического
   refresh endpoint нет: после истечения нужна новая привязка.
8. По отдельной команде студента вызови
   `PUT /events/{public_id}/registrations/me` с `{}`, `X-User-Token`, ключом клуба
   и новым ключом операции. Только после успеха показывай подтверждение записи.
   Отмена — `DELETE` того же пути; личный статус —
   `GET /events/{public_id}/participants/me`.

Привязка сама по себе **не записывает и не отмечает посещение**. Новый успешный
обмен того же студента для того же клиента отзывает прежний персональный токен.
Человек может отключить доступ: **«Личный кабинет → Подключённые боты →
подключение → Отключить»**.

Пример клиента:

```sh
python examples/club_api_client.py link --telegram-id 123456789 \
  --link-file link.json --idempotency-key link-example
# Человек даёт согласие в университетском боте.
python examples/club_api_client.py exchange --link-file link.json \
  --token-file user-token.txt
# Загрузи токен из файла в CU_CLUBS_USER_TOKEN через хранилище секретов.
python examples/club_api_client.py register EVENT_ID --idempotency-key register-example
python examples/club_api_client.py unregister EVENT_ID --idempotency-key cancel-example
```

Файлы привязки и токена содержат секреты: клиент создаёт их с правами `0600`
и не перезаписывает. Храни вне Git. У каждого студента собственный токен.
Токен студента не открывает персональные поля чужих встреч.

## 8. Посещение, импорт и ведомость

Предварительная запись и посещение — разные действия. Организатор с
`attendance:write` вызывает `POST /events/{public_id}/attendance`:

```json
{"full_name":"Иванов Иван Иванович","time_login":"i.ivanov","telegram_tag":"@ivanov_example"}
```

Логин обязателен, тег необязателен. Можно отметить студента без профиля бота;
повтор не создаёт второе посещение (`already_marked`). Отметка не создаёт
предварительную запись и не расходует её места. Не выдавай гостя за студента:
для него остаётся QR-путь в университетском боте.

Импорт XLSX:

1. Первый лист, первая строка — `ФИО`, `Логин в Тайме`, необязательный
   `Telegram-тег`. До 5000 строк данных, до 10 МБ. Шаблон доступен в разделе
   посещаемости университетского бота; макросы и внешние связи не поддерживаются.
2. `POST /events/{public_id}/attendance-imports`: multipart, одно файловое
   поле `file`, ключ операции. Это **только предпросмотр**, без записи посещений.
3. Покажи ошибки по строкам, сохрани `id` и `version` партии.
4. Для явно принятых организатором конфликтов ФИО вызови
   `POST /attendance-imports/{batch_id}/resolve` с
   `{"version":1,"rows":[2,5]}`. Номера — строки Excel, версия — из ответа.
   После каждого изменения используй новую версию.
5. После проверки организатором вызови `/confirm` для этой партии с её текущей
   `version` и отдельным ключом операции. При изменении встречи после загрузки
   создай новый предпросмотр; не обходи проверку устаревшей партии.

Ведомость: `GET /events/{public_id}/participants?format=xlsx` — файл,
`format=json` — страницы. `all_participants=true` включает регистрации и неявки;
`false` — только посетителей. Требуется `roster:read`.
Не размещай ведомость по публичной ссылке: в ней персональные данные.

## 9. Изменения и webhooks

Простой вариант — периодически читать `GET /changes?cursor=0&limit=100`.
После надёжной обработки сохраняй `next_cursor`. Пока `has_more=true`, читай
следующую страницу; при отсутствии новых данных курсор не сбрасывай.
Запись журнала: `id`, `type`, `event_id`, `version`, `occurred_at`, без ФИО,
почты и секретов. По изменению перечитай доступную карточку/ведомость.

Типы: `event.published`, `event.updated`, `event.cancelled`,
`registration.changed`, `attendance.changed`.

Для push-доставки создай свой получатель и вызови `POST /webhook-endpoints`:

```json
{"url":"https://your-bot.example.org/cu-clubs/webhook","event_types":["event.updated","registration.changed"]}
```

Замени иллюстративный адрес реальным публичным HTTPS-адресом своего бота, порт
443. Private/loopback IP, credentials в URL и redirects запрещены.
Ответ `201` содержит `id` и `signing_secret`: сохрани секрет отдельно от ключа API.
Обычный список секрет больше не выдаёт; идентичный повтор создания с прежним
ключом операции возвращает тот же успешный ответ.

Обработчик получателя:

1. Читает исходные байты тела до разбора JSON.
2. Проверяет `X-CU-Clubs-Timestamp` (Unix time, отклонение до 300 секунд)
   и `X-CU-Clubs-Signature`: `v1=` + HMAC-SHA256 от
   `timestamp + "." + raw_body`, ключ — `signing_secret`.
3. Использует сравнение с постоянным временем; готовая функция
   `verify_webhook_signature` есть в Python-клиенте. Часы сервера синхронизированы.
4. Надёжно сохраняет задание с дедупликацией по `delivery_id`
   (`X-CU-Clubs-Delivery`) и быстро отвечает `2xx`. Долгая обработка идёт отдельно;
   уже принятый дубликат также получает `2xx`.

Повторы сохраняют ID, доставка ровно один раз не обещается. Сетевые сбои,
`429` и `5xx` повторяются с задержкой; автоматический цикл ограничен восемью
попытками. Redirect не считается успехом. Webhooks могут приходить не по порядку;
пропуски восстанавливай через `/changes`.

`GET /webhook-deliveries` показывает статусы, попытки и безопасное описание ошибки.
После исправления получателя вызови
`POST /webhook-deliveries/{delivery_id}/retry` с `{}` и ключом операции.
Допускаются `failed`/`cancelled` с активным endpoint; ID сохраняется,
счётчик попыток не обнуляется. Отключение получателя:
`DELETE /webhook-endpoints/{endpoint_id}`, также с ключом операции.

## 10. Ошибки и помощь

Ответ содержит `error.code`, `error.message`, иногда `error.field`, и `request_id`.

| Ответ | Действие |
|---|---|
| `401` | Проверить ключ, персональный токен, срок/отзыв; при необходимости перепривязать студента |
| `403` | Проверить scope, полномочия выдавшего ключ и верификацию |
| `404` | Проверить ID и доступ клуба/коллаборации |
| `409 LINK_PENDING` | Дождаться явного согласия |
| `409 LINK_EXPIRED_OR_USED` | При потерянном ответе сначала повторить точный обмен с прежним ключом; иначе новая привязка |
| `409 IDEMPOTENCY_CONFLICT` | Не использовать ключ прежней операции с другими данными |
| Другой `409` | Прочитать код: например, нет мест, запись закрыта, устарело состояние; показать причину человеку |
| `412` | Перечитать встречу и согласовать правку заново |
| `428` | Передать `If-Match` |
| `413` / `422` | Исправить размер, поля или формат |
| `429` | Ждать `Retry-After`, снизить частоту |
| Тайм-аут / `5xx` | Повторять с задержкой; изменение — с прежним ключом операции и прежними данными |

Администрации сообщай время, метод/путь, HTTP-статус, `error.code`, `request_id`.
Не прикладывай ключи, токены, ссылки привязки, секрет подписи и ведомости.

## 11. Приёмка и обновление инструкции

Проверь на согласованных тестовых данных: чтение, публикацию, перенос, повтор
без дубля, конфликт версии, отказ/согласие привязки, запись/отмену, повтор отметки,
импорт с конфликтом, подпись/повтор webhook и отзыв обоих видов доступа.
Нового студента можно проверить полностью после подключения почты.

API проверен автоматическими тестами на синтетических данных; целое подключение
реального независимого клубного бота ещё не принято. Доступность запущенной схемы
и отказ без ключа не заменяют приёмку твоей конкретной интеграции.

При изменении API разработчик в том же изменении обновляет эту инструкцию,
контракт и пример клиента. CI сверяет список методов/путей с кодом; изменение
смысла полей и бизнес-правил проверяется отдельно при ревью.
После настройки публичного HTTPS здесь должны появиться настоящий адрес и
обновлённый порядок подключения. Адреса и ограничения выше относятся к текущему выпуску.

импорт, webhooks и порядок поддержки документа.
